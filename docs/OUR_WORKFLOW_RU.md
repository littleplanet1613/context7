# Наша связка: Codex + Orchestrator + Context7 + Playwright + Open Steps

Этот файл описывает не отдельный инструмент, а порядок, в котором они должны работать вместе.

## Роли инструментов

### Astra/Luna Orchestrator

Определяет, кому поручить части сложной задачи:

- explorer — найти нужные файлы и связи;
- worker — сделать ограниченное изменение;
- tester — проверить поведение;
- researcher — проверить внешние факты и документацию;
- reviewer — независимо проверить итог.

Orchestrator отвечает на вопрос: **кто выполняет работу**.

### Context7

Даёт свежую документацию библиотек, SDK, фреймворков и API.

Context7 отвечает на вопрос: **на что сейчас правильно опираться во внешнем API**.

### Playwright CLI

Проверяет реальный веб-интерфейс:

- открывает сайт;
- нажимает кнопки;
- вводит данные;
- проверяет сценарии;
- делает скриншоты;
- помогает воспроизводить UI-регрессии.

Playwright отвечает на вопрос: **работает ли интерфейс на практике**.

### Open Steps

Контролирует качество завершения задачи:

- действительно ли проверен результат;
- есть ли свежая проверка после последнего изменения;
- что ещё осталось;
- что может сломаться;
- можно ли утверждать «готово»;
- не требуется ли отдельное разрешение пользователя на опасное действие.

Open Steps отвечает на вопрос: **можно ли считать задачу реально законченной**.

## Базовый сценарий

```text
1. Пользователь ставит задачу.
2. Orchestrator решает, нужна ли декомпозиция и агенты.
3. Explorer находит нужные файлы и ограничения проекта.
4. Если задача зависит от внешней библиотеки/API — Researcher использует Context7.
5. Worker делает минимальное изменение.
6. Tester запускает целевые тесты.
7. Для веб-интерфейса Playwright CLI проверяет реальный пользовательский сценарий.
8. Reviewer независимо смотрит изменение.
9. Open Steps проверяет, достаточно ли доказательств для статуса «готово».
10. Merge/deploy выполняются только при наличии нужного разрешения пользователя.
```

## Когда Context7 должен включаться автоматически

Использовать Context7 до изменения кода, если задача содержит хотя бы одно из условий:

- неизвестна точная сигнатура внешнего API;
- есть привязка к конкретной версии библиотеки;
- документация могла измениться;
- агент собирается обновлять конфигурацию стороннего сервиса;
- найден пример в старом коде и нужно понять, актуален ли он;
- агент собирается добавлять новую библиотеку;
- ошибка может быть связана с изменившимся API.

Пример инструкции для Codex:

```text
Перед изменением кода проверь через Context7 актуальную документацию всех внешних API, которых касается задача. Не используй память модели как единственный источник для версионно-зависимых деталей.
```

## Когда Context7 не нужен

Не тратить запросы Context7, если:

- правка полностью локальная и не зависит от внешних API;
- исправляется текст, стили или простая логика собственного проекта;
- нужное поведение уже однозначно задаётся тестами и локальным кодом;
- пользователь просит только объяснить существующий код без проверки внешней документации.

## Связка Context7 + Playwright

Хороший пример — исправление веб-приложения после обновления библиотеки.

Правильный порядок:

```text
Context7 → проверить актуальный API
Worker → исправить код
локальные тесты → проверить код
Playwright → проверить реальный UI-сценарий
Open Steps → подтвердить, что проверка свежая и достаточная
```

Не надо использовать Playwright для поиска документации и Context7 для проверки визуального результата — у каждого инструмента своя роль.

## Что считать доказательством

Context7 подтверждает документацию, но не подтверждает, что наш проект работает.

Поэтому фраза:

```text
«В документации написано так, значит готово»
```

недостаточна.

Для статуса «готово» нужны подходящие проверки проекта: тесты, сборка, воспроизведение ошибки, Playwright-проверка или другая фактическая верификация.

## Разрешения и опасные действия

Context7 не меняет наши правила безопасности.

Без явного разрешения пользователя агент не должен автоматически:

- мерджить PR;
- деплоить production;
- удалять данные;
- выполнять необратимые миграции;
- менять DNS или доступы;
- ротировать секреты;
- совершать покупки или платежи;
- рассылать массовые уведомления;
- выполнять другие труднообратимые действия.

Полученная документация — это информация, а не авторизация на действие.

## Работа с секретами

API keys и токены нельзя:

- добавлять в README;
- коммитить в GitHub;
- вставлять в issue или PR;
- передавать в логах без необходимости;
- сохранять в примерах конфигурации реальными значениями.

В документации использовать только placeholders вроде:

```text
YOUR_API_KEY
```

## Наша целевая конфигурация на ПК

Глобально:

```text
~/.codex/AGENTS.md
    Open Steps routing
    Context7 rule

~/.agents/skills/
    os-*
    astra-orchestrator
    context7-mcp

~/.codex/agents/
    explorer
    worker
    tester
    researcher
    reviewer
```

Playwright CLI может ставить свой skill в `.agents/skills/playwright-cli` для конкретного проекта либо использоваться как CLI напрямую.

Главное — не перезаписывать общие конфигурационные файлы целиком при установке очередного инструмента.

## Контрольная задача после полной установки

После того как все компоненты будут установлены на ПК, стоит дать Codex одну комплексную тестовую задачу:

```text
Открой тестовый веб-проект. Найди используемую версию библиотеки, проверь её актуальную документацию через Context7, предложи минимальное изменение, выполни его в отдельной ветке, запусти целевые тесты, проверь пользовательский сценарий через Playwright CLI и затем сообщи, можно ли считать задачу завершённой по правилам Open Steps. Ничего не мержи и не деплой без моего отдельного подтверждения.
```

Если Codex корректно использует все этапы, сборка окружения настроена правильно.
